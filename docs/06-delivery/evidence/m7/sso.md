## Actual trust boundaries

Company sign-in uses the pinned Better Auth SAML verifier, tracked SP requests, signed assertions, issuer/audience/time checks, SHA256 policy and a namespace-aware bounded envelope. Metadata is supplied by an administrator; the app never fetches an arbitrary metadata URL. `@xmldom/xmldom@0.9.12` is a directly pinned MIT parser already present transitively in the lockfile. DTD/entities, wrapping, multiple assertions/statements, ambiguous endpoints, weak signatures and unsupported encrypted assertions refuse. Metadata and callback bodies have explicit bounds. A successful signature cannot supply app roles, a company ID, or a recent local-factor receipt.

Operator trust is a separate action. `inspect-sso-provider <provider ID>` shows public trust details and a canonical SHA256 fingerprint. After reviewing actual domain ownership and metadata, the operator runs `verify-sso-domain <provider ID> <reviewed SHA256>`. Verification compares the submitted fingerprint under the same auth transaction/row lock that records trust; it never silently refreshes the expected fingerprint. Changed trust fields reset auth trust and remove that provider's SSO assurances. Activation and every admission require combined current app and auth trust. The UI reflects this combined state even if the app's older domain flag still says verified.

Signed SAML primary time comes only from the exact POST body that the native verifier accepted, with matching issuer and subject and exactly one signed Assertion/AuthnStatement. Missing/old time never becomes callback time. The operator OIDC path now wraps the actual supported native profile/verifier path: the exact ID token must pass native signature, issuer, configured audience and nonce verification; its signed subject must equal the actual returned profile subject. Only signed finite `auth_time` supplies primary freshness. Unverified userinfo time, missing ID tokens and callback/session timestamps cannot bootstrap passwordless enrollment. Native login behavior stays separate from that fresh-primary decision.

Native provider callbacks for enrolled accounts also pass through the unchanged native second-factor handler. Before that handler deletes the provisional full session, request-local state captures the verified source. After the native handler issues a challenge, one short auth transaction promotes its real challenge and attempt identifiers and stores the opaque bridge. The browser receives only the signed `2fa-idp-…` identifier and the real local code form. The original source session is deleted, downstream proof hooks observe no full session, and earlier full cookie headers are removed. A native trusted-device decision remains native behavior; it does not mint a fresh local-factor assurance.

The required bridge namespace is `ensemus-idp-factor:v1:` in auth-only `identity.verifications`. Its keyed identifier/UUID covers the actual native challenge. Its bounded value contains only source/user/account IDs, provider/issuer configuration, subject/configuration/body-or-token hashes and original signed authentication time. It stores no raw assertion, ID token, subject, email, code or password. Expiry is exactly the native ten-minute challenge expiry. Native attempt counters are retained. After the actual factor and global replay admission succeed, completion checks current account, actual resulting session, provider trust and current company membership/link. It atomically consumes the exact protected bridge with the primary receipt. Missing/expired bridge state for an IdP-prefixed challenge always refuses; it cannot become an ordinary password challenge. Ordinary credential challenges do not trigger provider discovery. Proof and full cookie forwarding happen only after these checks.

Replicas require the same auth key, provider configuration and clock policy. Key/config changes invalidate old receipts; seamless cross-key receipt rotation is not implemented. SAML/native account setup and app membership authorization cross roles through separate short transactions, without a SQL transaction spanning an external request. Live privilege checks still recheck current membership, link and provider authority: a late receipt cannot restore a disabled member. Remote IdP session revocation beyond the configured signed protocol/SCIM is not invented introspection.

## Company policy, provisioning and interface

The policy service checks a fresh real manager and recent auth-role factor proof; agent/service identities cannot manage it. SSO remains optional by default, auto-join is explicit member-only, and current active owners retain the existing recovery path. The parent-approved narrow `assertTenantSignIn` change rechecks the actual active membership, active subject link, active verified company connection and current auth provider trust. Its 0401 SSO-assurance read policy also requires the actual matching unexpired session. App-readable metadata is limited to session ID/user/expiry and tenant-linked provider ID/verified flag; tokens, provider configuration and app proof writes remain ungranted. A late auth receipt after SCIM disable therefore cannot revive access when a human later enables the membership while its provider link stays deprovisioned. Subject identity is provider + IdP issuer + external subject, preventing accidental linking between providers. SCIM uses a one-time displayed hashed bearer token, connection scope, fixed sanitized errors, bounded requests/filtering/pagination and explicit supported active/deactivate operations. Deprovisioning, human membership changes and last-owner checks share the existing member advisory-lock order. Human explicit re-disable clears only the matching member's deprovisioned-provider reactivation receipts through authored migration 0403.

Pages/actions cover company sign-in, completion, metadata/trust readiness, activation, member auto-join, one-time token creation/revocation and existing company policy. They use shared primitives, ordinary forms, plain labels and real operator commands. No fake domain-verification, reset or forced-reauthentication button is added. Lost pending MFA keys still require the existing documented operator reset route; a provider callback cannot manufacture a newer authentication time.
