## Behavior and boundary

Every supported archive format, including legacy core, `/1`, `/2` and current unpublished `/3`, lacks sufficient trustworthy original-input lineage to create an ordinary human or generated artifact. The operator now retains each verified file in separate inert custody. It creates no `work.artifacts` row, no live `work.work_artifacts` link and no fabricated human creator, empty input inventory or promotion receipt. Existing0208/0211 serving and pre-put guards are unchanged.

The actual encrypted parser validates all archive parts and strict records first. The0409 immutable manifest and part receipts must be committed before0415 independently matches the exact metadata-record digest, binary part path/hash, bytes/hash and size. A private SQL writer header commits before the first object put. Its key is exactly `{organizationId}/archive-quarantine/{importId}/{sourceArtifactId}/{writeToken}`, with UUIDs only. Untrusted names and MIME types never form storage keys; storage and downloads use `application/octet-stream`.

Only an actually fulfilled put followed by exact bounded read-back can settle as quarantined. A genuinely completed put whose read-back or current authority fails settles closed for cleanup. A rejected/ambiguous put remains an active unknown writer; replay refuses without another put, including when HEAD reports absence. The CLI's actual S3 adapter disables SDK retries for this path. A process crash can leave a retained `writing` header: no automatic replay or absence-based success repairs that uncertainty.

Only the current native-session owner who is the actual admitted import custodian may download for review. The SQL session/person, source/record closure, classification, permission and file receipt are rechecked before and after object I/O, with no SQL transaction over the read. The page exposes safe ID/status/size when input authority cannot be proven, withholding filenames, MIME types and download links. A human may review the bytes and deliberately attach them through the existing ordinary-human Work upload pipeline, producing a new artifact ID. No automatic rehydration or provenance approval is implemented.

## Conservative unknown-input fence

These files have unknown possible inputs; this change does not invent actual lineage. Admission and serving conservatively require **every current Knowledge source and retained structured-record catalog entry** to be live, readable by the actual named custodian and no more sensitive than the archived file. Kinds include Work, project, client and custom record, through the current central metadata helpers. Any retained relevant tombstone or closed catalog blocks admission/serving, including an unrelated source or record. This can prevent an import or review even when the real file never used that input. It is an explicit privacy limitation until an actual trusted lineage/rehydration protocol exists.

A per-organization archive/source/record/tombstone advisory barrier linearizes header admission against the first source/catalog birth or closure. Sorted metadata/source locks use `FOR SHARE NOWAIT` under that barrier; an inverse writer order refuses rather than waits in a deadlock. A header commits before closure and is included by cleanup, or the closure commits first and admission refuses. An active-organization lock also refuses new archive writes during tenant erasure. More than2000 current sources or2000 retained structured entries refuses proof rather than truncating it. Native list/read SQL has a2-second statement budget; actual scale/performance gates remain unrun.

Fixed metadata-only migrator functions use forced RLS and a saved/restored private named-viewer scope to call existing current ACL helpers. No app role membership, factor/account body, source/document body, secret, IdP payload or provider configuration grant is added. Transaction GUCs are selectors, not unforgeable credentials; native identity provenance and the trusted operator/parser remain separate boundaries.
