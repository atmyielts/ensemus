# Isolated generated-data load measurements

This harness has not been run against a stack. It performs bounded authenticated API reads using Node fetch/timers only. Profile dataset quantities are declared test inputs, not a fixture seeder or capacity result. Prepare those rows and independently record evidence before interpreting latency. Small/medium/growing use the plan's approximate 20/100/300-person personas; the aggregate profile has multiple isolated tenants. Every other number is a tunable generated test parameter. Retention has no duration default and the harness performs no retention mutation.

There is **no target URL default**, no account creation against an unknown host and no built-in production credential. Create dedicated generated accounts in an isolated deployment using the existing test fixture/bootstrap facilities. Save a private JSON fixture with `kind: "ensemus-generated-load-fixture-v1"`, `generated: true`, `complete: true`, and `tenants: [{organizationId, actors: [{userId,email,cookie}]}]`. All user/organization IDs must be valid and distinct; actor emails must be generated `load-…@example.invalid` addresses, and each concurrent worker needs a distinct account/session. The manifest is an operator assertion backed by the fixture-creation evidence, not proof merely because its flag is true. Never put it in Git or attach it to a report. All reports use anonymous tenant indexes and discard response bodies, cookies, IDs, names and error text.

`seed-fixture.mjs` creates the concurrent generated accounts, organization memberships and profile Work Units through the actual forms/API, without agents. It requires an explicit **loopback test origin**, reserves a private new fixture file, and records partial fixture evidence with `generated: false` on refusal. It uses the existing test form driver and its local-test certificate setting, so it refuses remote hosts. It does not populate documents, clients or projects; its dataset counts record that explicitly, and those profile inputs still need separate fixture preparation. No seeding command was executed by this source work.

```text
node tests/load/seed-fixture.mjs --profile small --base-url <explicit-loopback-test-origin> --out <new-private-generated-fixture.json>
```

Provide a separate private context JSON with `environmentRef`, `release`, `networkLocality` (`loopback`, `same_host`, `same_network`, `remote`, `unknown`), and `hardware: {cpuModelRef, logicalCpus, memoryBytes, osRef}`. References are bounded machine codes. Record the true reference hardware and traffic inputs. The report does not extrapolate from them.

```text
node tests/load/run.mjs --profile small --base-url <explicit-origin> --fixture-file <private-generated-fixture.json> --context-file <measurement-context.json> --out <new-report.json>
```

Optional `--profile-file <json>` overrides generated parameters, and `--scenario <A-L>` selects the named run. A is business API reads without agents; it does not claim CRUD, recovery, isolation or accepted-outcome correctness. Every attempted read, including timeout, HTTP refusal and body-limit failure, contributes to web latency/error rate. TTFB counts only responses whose headers arrived; network failures remain in the full web measurements. Empty measurements are null, not zero. Fairness is worst/best tenant p95 only when every tenant has a positive sample. Event-loop delay is measured in the harness process; it is not the server's event-loop metric. Server loop/heap/pool observations still need the runtime exporter.

Scenarios B–L require an explicit reviewed local `--controls <path.mjs>` module exporting `exercise({scenario, profile, tenants, baseUrl, runRef, signal})` and `verify({scenario, tenants, baseUrl, runRef, signal})`. There is no default fault injector or fake-success control. `exercise` runs concurrently with business reads. Controls must respect the abort signal, stop/recover their own induced fault on cancellation, and finish within the explicit `scenarioTimeoutMs` tuning input; a deadline fails verification. For B it must enqueue real bounded agents using the installed M4 test interface; C ingests generated data, D injects model timeout/rate limits, E restarts Temporal, F performs approved DB failover, G checks cache invalidation, H routes across actual replicas, I crashes/reconciles an external effect, J verifies offline Sovereign startup, K revokes generated sources, and L rotates generated BYOM credentials. Environment-specific control code is trusted operator code and must be reviewed before import. Do not point it at a live customer environment.

`verify` returns observed `conditionInduced`, `loadOverlappedReads`, `recovered`, `isolationVerified`, `noDuplicateEffects` booleans, and optional measured `agentQueueWaitMs` array. A missing/false proof fails the scenario. The control must establish from actual timing that induced load overlapped the business reads; merely starting two promises is insufficient. B additionally requires nonempty queue-wait measurements. Do not return customer content or treat a submitted agent request as a verified accepted outcome. The source slice supplies the protocol and refuses missing controls; those environment-specific scenario bindings and their actual fault evidence remain owed.

Optional `readVerifiedOutcomeCost({runRef,organizationIds,scenario})` must read the actual M4 ledger for that exact generated run/cohort and return `{source:"actual_m4_ledger",runRef,currency,totalCostMicros,verifiedOutcomes}` with the matching run reference. Until a reviewed binding exists the report says `owed`; no price/FX/credit conversion is assumed. The report preserves the exact money numerator and outcome denominator rather than rounding an invented unit price. Queue wait and cost are separate from HTTP latency.

Output is reserved with exclusive creation and private permissions before any requests. Existing evidence is never overwritten. Exit 0 means this bounded measurement finished with no failed web requests and no failed scenario verification; it is not production acceptance. Exit 1 retains a report showing request/scenario failures, and exit 2 means configuration/execution refused or failed. Preserve release, hardware, traffic, control-code reference and independent fixture evidence beside the report. No production capacity claim is made.
